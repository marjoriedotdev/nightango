# BetterChatango and Chatango protocol

This document describes what Nightango knows about the BetterChatango client (vissle.me) and the Chatango protocol. Each point was checked in the BetterChatango code, in the official Chatango client or in a reference library. A frame or format missing from here has no known source: do not send it (see [ADR-0002](adr/0002-no-invented-frames.md)).

## Reference sources

- BetterChatango: its code loaded by `https://vissle.me/client/start`, in particular `inject.js` (`kickingoff`, `DENIED`, `socketEvent`, `window.onoffline`, `saveMessage`, `renderMessage`). A read-only copy, downloaded on 2026-10-19, is in `reference/torch/` (`start.js`, `inject.js`, `client.html`, `client.css`). An `inject.js:NNNN` reference points to a line of this copy. The code served by vissle.me may have changed since: when in doubt, compare with the online version.
- Official Chatango client: texts of the "Connection lost" window, private history format, "Delete" button, media prefixes.
- chadango (Go): https://github.com/n0h4rt/chadango
- chatango-lib (Python): https://github.com/neokuze/chatango-lib
- ch.py (Python, older): https://github.com/asl97/ch.py
- vissle: `vissle.me/js/track.js` for the profile tracker. This script is not copied into `reference/torch/`: it is not part of the BetterChatango client and no known license covers it.

## BetterChatango startup

- The official BetterChatango bookmarklet adds the script `https://vissle.me/client/start`. BetterChatango then builds its page and exposes the global variables `client`, `chatango`, `sidebar` and `torch`.
- These variables live in the page. The page code (`skin-page.js`) reads them with an injected probe script, which stores them in `window.__betterChatangoRefs`.
- The technical group `torch.environment` is ignored by the bridge.

## Events

- `client.on(evt, cb)` is a `CustomEvent` on `document` named `chatango_<evt>`. The callback receives the event, not the client.
- The bridge detects sign-in through the `clientLogin` event, and as a fallback by polling `client.user.name`.

## Incoming frames

- The tables `client.event.group` and `client.event.private` are called with `(client, socket, room, argsArray)`. The frame is already split on `:`.
- The BetterChatango dispatcher tests `command in table`. The bridge therefore wraps these tables and adds the missing handlers to them.

### Group members

Received frames only: nothing is sent.

- `g_participants` (and `gparticipants`, after its first field): entries separated by `;`, fields by `:`. `t[1]` session timestamp, `t[2]` anon id, `t[3]` account name or `None`, `t[4]` guest name or `None`. BetterChatango shows a guest named `#t[4]` and an anon through `getAnon(t[2], t[1])` (`parseParticipant`, `inject.js:10378` to `inject.js:10424`, line `inject.js:10422`).
- `participant` (`inject.js:3409` to `inject.js:3538`): `data[0]` action (0 leave, 1 join, 2 change), `data[2]` anon id, `data[3]` account name or `None`, `data[4]` guest name or `None`, `data[6]` session timestamp. This timestamp links the frame to the `g_participants` entry (`inject.js:3413`).
  - Action 0: the session leaves, account or guest (`inject.js:3414` to `inject.js:3429`).
  - Action 1: a session joins, account (`inject.js:3430` to `inject.js:3453`) or guest if `data[3]` is `None` (`inject.js:3454` to `inject.js:3457`). BetterChatango shows the guest as an anon. The bridge reads `data[4]` as in `g_participants`: a guest who joins already named keeps their name.
  - Action 2: the session changes identity without leaving the group (`inject.js:3458` to `inject.js:3516`). BetterChatango tests in this order:
    1. `data[4]` set: the anon of this session takes the guest name `#data[4]` (`inject.js:3459` to `inject.js:3467`).
    2. `data[3]` is `None`: the session becomes anon again. BetterChatango removes the row linked to the session, except the owner's row which it sets offline, then emits `memberLogout` (`inject.js:3468` to `inject.js:3480`).
    3. Otherwise: the session carries the account `data[3]`. BetterChatango emits `memberLogin` (anon to account), `memberSwitch` (other account) or `memberChange` (same account), adds the account row and removes the old one (`inject.js:3481` to `inject.js:3515`).
  - Several sessions of one account: BetterChatango keeps a single visible row, the oldest (`inject.js:3517` to `inject.js:3536`).
- The bridge (`live-bridge.js`) keeps, per group, a table from session timestamp to `{ account }`, `{ guest: '#name' }` or `{ anon: true }`, filled by `g_participants` and kept up to date by `participant`. On each change, it emits `guests`: guest names without duplicates, sorted, and the anon count. The guest name is lowercase, like the author of their messages, so that the member card and the ban find them.
- An account is in the member list as long as at least one session in the table carries it. The bridge emits `member` (action 1) when an account gains its first session and `member` (action 0) when it loses its last one, for actions 0, 1 and 2. A session unknown to the table (frame received before `g_participants`) enters it through actions 1 and 2. Action 0 on an unknown session removes the account `data[3]` if it has no other session in the table. The signed-in user always stays in the list (`app/root.js`).

## Sending

- A frame goes out through `client.socket(gid, frame, errorText)`.
- `client.socket` catches every error itself: on a connecting, closing, closed or missing connection, it only shows `errorText` and the connection state as a system line, sends nothing and returns normally (`inject.js:4622-4670`). The bridge therefore hands it a frame only when the socket of the target connection is open (`readyState` 1, `client.groups[gid].socket` or `client.private.socket`). Otherwise nothing leaves, the action reports a failure and leaves the state as it was, and the bridge shows the error text followed by "Try again once you're reconnected to #g." (or "to private messages"). A group message or a PM is checked before it is built: Root shows its own failure, and an upload shows its link ("The file was uploaded, but the message was not sent.").
- For a message, `client.sendMessage(text, true, gid)` returns the styled body without sending it. BetterChatango expects HTML: the text must be escaped (`&`, `<`, `>`).
- The bridge inserts `<r{ref}/>` for a reply, then sends `bm:{id}:{flag}:{body}`.
- For a PM, `client.sendMessage(text, true, 'private_message', name)` returns the body, which the bridge sends as is: `msg:{name}:{body}` through `client.socket('private_message', …)`, like `sendMessage` without length (`inject.js:5206`, `5266`). Each build draws a new `<i…/>` PM key (`inject.js:5141`, `5177`): building once keeps for the shown PM the key that was sent, which a reply can target. `client.socket` archives the sent PM under `client.private.focus`, the conversation BetterChatango considers open, and archives nothing while it is `false` (`inject.js:4633-4645`). The record carries one's own name twice: only its `target` ties it to the recipient. A PM can leave after the user switched to another conversation or to a group, like the link of a file upload. The bridge therefore sets `client.private.focus` to the recipient for the time of the send, then gives it back the shown conversation (`focusPm`).
- Group message length: 2900 characters at most (`room.character`, `inject.js:3086`, reset to 2900 on each `groupflagsupdate`, `inject.js:3924-3928`). BetterChatango counts the `String.length` of the body that `sendMessage` builds in length mode, without the `bm:{id}:{flag}:` prefix (`inject.js:4989-4994`): own style, `<br/>` and entities count. `liveBridge.measure` counts the same body, with the `<r…/>`, the `<e…/>` or the quote that sending inserts. BetterChatango shows this count without blocking sending. Nightango shows it at 300 remaining characters or fewer and refuses to send beyond the limit. A message refused by Chatango gets `msglexceeded` (`inject.js:3861-3863`), shown as a notification by the bridge.
  - BetterChatango lowers the limit to 850 for a group with the `NO_REPETITION` flag (`inject.js:3106-3108`, `3924-3925`). This name is missing from `chatango.flags.group`, so the limit is never applied, and without a source Nightango does not reuse it. PMs (9000 in BetterChatango, `inject.js:8825`) have no count.
- Message references `<r…/>` and `<e…/>`: id without the trailing `=`, `-` replaced by `hypheN` and `_` by `underS`.
- Editing a message (BetterChatango `sendMessage`, `inject.js:5236-5241`): `bm:{id}:{flag}:<n…/><f …><e{ref}/>{content}`. The body is that of an ordinary message, own style and emphasis included, and `<e{ref}/>` targets the original. The bridge inserts it at the same place as `<r…/>`, never together with it, and keeps the channel of the original. Failure text: "Your message could not be edited." An unchanged text is not sent.
  - Receiving (BetterChatango `displayEdit`, `inject.js:5497-5536`): same author required. In real time, the edit replaces the text of the original. In the history, received from newest to oldest, it replaces it only if the original is not already edited. An edit whose original is not loaded is shown separately, marked edited. When the original then arrives through the history, it takes the text of the most recent edit and the edits shown separately disappear.
  - Limit specific to BetterChatango: 9 edits per message (`data-edits`, which starts at 1, refused at 10, `inject.js:5466-5467`). No time limit: Chatango only sees a new message. How the official client renders edits is not checked.
  - Deleting (BetterChatango `delete` action, `inject.js:7444-7448`): `delmsg:{id}` of the original, then `delmsg:{id}` of each of its applied edits. BetterChatango shows a message only once its final id is received (`u` frame): the bridge therefore deletes only the edits whose final id it knows. A `delete` received for an original also removes from the message log its edits shown separately.
- Quoting a message (BetterChatango `sendMessage`, `inject.js:5245-5252`): ``bm:{id}:{flag}:<n…/><f …>{emphasis}@{name}: `{quoted}` {content}``. The bridge builds the body of an ordinary message, then inserts the quote at the start of the content: after `<n…/><f …>` and the opening `<b>`, `<i>`, `<u>` of the style. `{name}` is the author's name as they are mentioned (without the `#` of a temporary name, no quote for an anon), `{quoted}` their text without backticks, with line breaks replaced by a space, trimmed, then escaped (`&`, `<`, `>`). No `<r…/>`: the quote does not point to the original. Failure text: "Your quote could not be sent." Nothing is shown before Chatango sends the message back.
  - BetterChatango inserts the quote at `content.lastIndexOf(typed text)` (`inject.js:5246`). When its Markdown changed the typed text, this index is -1 and the quote ends up in the wrong place. Inserting at the start of the content gives the same result in all other cases. The bridge reads the style emphasis from the BetterChatango checkboxes, like `sendMessage` (`inject.js:5145-5150`, `5182-5184`): a Markdown emphasis at the start of the typed text stays after the quote.
  - Receiving (BetterChatango `renderMessage`, `inject.js:8099`): `` @name: `text` `` (name of 1 to 20 letters or digits, no line break between the backticks) is shown as a quote, the name as a mention. Nightango rebuilds it as React elements from the text, in each emphasis segment.

## BetterChatango warnings

`client.systemMessage(...)` and `client.setNotice(...)` are intercepted by the bridge, then shown as a notification (toast), never in the message log: BetterChatango addresses them to the group it believes is open (`client.focus`), not necessarily the group concerned.

- Friend presence: BetterChatango emits "X is now online.", "…offline." or "…idle…" with `unique: "status"` and without `group`, for the PM it believes is open (`status` and `idleupdate` handlers, `inject.js:4187` and `inject.js:4294`). The bridge silences them: the friend list already shows presence.

## Session and reconnection

- `kickingoff` (`private` table): the account signed in to PMs elsewhere. BetterChatango closes its private connection and announces it through `systemMessage`. The bridge emits `session` (`kicked`) and silences this notice. There is no automatic reconnection, otherwise the two windows would keep taking the session from each other.
- `DENIED` (`private` table): expired token. BetterChatango answers with a blocking `alert()`. The bridge does not call it and emits `session` (`denied`). Only a reload gets out of it.
- BetterChatango never reconnects on its own. When a socket closes, it shows "You have disconnected from #g" with a Reconnect button. The bridge silences this notice: the Nightango connection banner replaces it, and this Reconnect calls `client.connect` outside the bridge, which opened a second socket when an automatic retry followed.
- BetterChatango takes `window.onoffline` and `window.ononline`. The bridge listens to `offline` and `online` through `addEventListener`, without touching the BetterChatango properties.
- When the network comes back (`online`) and when the page returns to the foreground (`visibilitychange` to `visible`, `pageshow` of a page restored from the cache), the app (`reconnectClosed()` in `app/root.js`) reconnects the joined groups whose socket is closed, then the private connection if it is closed. The private connection stays down after `kickingoff` or `DENIED`.
- Automatic reconnection (`scheduleRetry()` in `app/root.js`): when an open connection closes (joined group or private connection), the app retries it after 3 s, then 10 s and 30 s after each failure, three attempts at most. A failed `reconnectClosed()` retry chains the same way. Nothing is retried if the page is hidden, if the network is missing or after `kickingoff`, `DENIED` or `offline`. Once the attempts are used up, the session loss banner keeps its Reconnect button. The journal records each scheduled attempt and the give-up.
- An automatic retry of a group that is not shown does not go through `setFocus` (`reconnect(gid, true)` of the bridge): the BetterChatango focus stays on the shown group. Chatango sends the history (`i`) to the new socket without a request, before `inited`: the BetterChatango environment group reads its configuration there (`inject.js:3188-3224`). The participant list is requested when the group is shown (`setFocus`).
- `client.connect(gid)` goes through `socketEvent`. As long as `gid` is in `client.cache.connect`, the request is ignored and the promise never settles. BetterChatango removes `gid` after each attempt. The bridge does the same around each of its calls (`connect()` in `live-bridge.js`), otherwise a second Reconnect has no effect.
- BetterChatango rejects an attempt after 10 s only for the group it recorded last in `client.cache.connecting`, a single slot (`inject.js:5613`, `5699-5704`). An attempt whose handshake hangs, or whose socket closes before `inited` while its group is not `client.focus` (`inject.js:5668-5697`), never settles on its side. The bridge gives each of its attempts the same 10 s: on expiry, the attempt fails like any other, the journal notes "no answer after 10 s", and the automatic reconnection delays apply.
- `socketEvent` creates its socket synchronously and keeps it to itself until `ok` registers it in `client.groups`, or `OK` in `client.private` (`inject.js:5631`, `3185`, `4037`). The bridge picks it up by replacing `window.WebSocket` for the duration of the `client.connect` call only. A failed attempt closes this socket while `ok` has not registered it: a late answer would give BetterChatango a second socket for the connection. A registered socket stays open even if `inited` misses the 10 s, as in BetterChatango: it carries the group, and closing it would restart the automatic reconnection from its first attempt, endlessly on a slow link.
- Leaving a group: `client.disconnectFrom(gid)` only closes the socket registered on `ok`, and only if it is open (`inject.js:5714`). The bridge also cancels the pending attempt of the group, which closes the socket still connecting. The follow-ups of a join or a reconnect (`setFocus`) do nothing for a group left in between.
- The texts of the Nightango "Connection lost" window are taken from the official client.
- The diagnostic journal wraps the `WebSocket` constructor to record the opening, the names of the received session frames and the closing with its code. It never observes `send`: `bauth` carries the password (`inject.js:5618`). Details: [ADR-0011](adr/0011-diagnostic-journal.md).

- The two calls that carry the password, `vissle.me/client/login` and `script/setcookies`, belong to the BetterChatango sign-in, on its screen. Our code does not touch them.
- Nightango neutralizes those that contradict its media settings: at sign-in (`clientLogin`), the bridge replaces in memory `client.renderYouTube` (oEmbed) and `chatango.getBackground` (`msgbg.xml`, for one's own account as for authors) with a function that does nothing. Once the bridge sees the sign-in, no `www.youtube.com/oembed` or `msgbg.xml` request leaves BetterChatango in live anymore. Nightango reads `msgbg.xml` itself according to "Message backgrounds" (see Message background). Nothing is written to `localStorage["settings"]`: BetterChatango without the skin keeps its behaviour. The prototype is not concerned.
- PMs at startup (`connect_start`, see BetterChatango startup settings): 6 s after sign-in, BetterChatango clicks its own PM tab (`inject.js:1365-1369`), whose handler opens its PM screen (`inject.js:10601-10703`). This screen sets `client.focus` to `private_message`, which the bridge never does (see Private history). Then it either sets `client.private.focus`, which its PM sound follows (see What stays in BetterChatango), to `false` through `Private.initiate` (`inject.js:8838`), or opens the PM shown in Nightango through `Private.setFocus`, which marks it read in the database (`inject.js:8961`, `inject.js:8974`). If the private connection is not open yet, it also opens one itself (`inject.js:10611-10614`) and reads `check_pmr` from vissle (`inject.js:10631`). The bridge neutralizes it at sign-in like the two calls above: it replaces in memory the `click` method of this tab (`[data-sidebar="private"]`) with a function that does nothing. The other programmatic clicks on this tab come from the hidden BetterChatango screen: `/chat` typed in its composer without a name or before its private connection (`inject.js:7356`), its chat icon (`inject.js:10598`) and its Reconnect for private messages (`inject.js:5684`), which the bridge does not show (see Session and reconnection). Nothing is written to `localStorage["settings"]`: `connect_start` keeps its value, and BetterChatango without the skin keeps its behaviour.
- Whether a `lazy` image or a `<video>` in a detached element loads is not established: it depends on the browser.
- These only happen from the BetterChatango screen, so never in live: `check_pmr` (on click on the BetterChatango PM tab, `inject.js:10601`, whose programmatic clicks the bridge disables, see above, and which the bridge makes itself, see PM restriction), `check_block` (BetterChatango sends `connect:` only on click in its screen, and the bridge does not call its `connect` handler, see Friend presence), the uploads from its Upload window (Nightango sends its own through the closed list, see File uploads (vissle)), `/api/v1/uploads`, `/api/v1/who` (which Nightango makes itself on click, see Linked accounts (vissle)), `/api/v1/profile`, `/track`, group registration (`vissle /chatango/room`).

## Private messages

### Private history

- IndexedDB database `<username>_history`, version 1, object store `messages` (keyPath `ts`), index `target_idx` on `target`, `target_read_idx` on `["target","unread"]` and `target_ts_idx` on `["target","ts"]` (`inject.js:10670-10675`). `target_ts_idx` orders a member's PMs by key: BetterChatango uses it for read marking and paged reading.
- BetterChatango opens this database only from its own private screen. The bridge opens it with the same schema, then assigns it to `client.database.pm`.
- Record (BetterChatango `saveMessage`, same format as the official client): `{ target, ts, data, unread }`. `data` is the full raw frame `msg:name:…:ts:flags:body`, tags included.
- BetterChatango reading: when a PM opens, the 50 most recent through `target_idx` in `prev` order (`inject.js:8939-8970`). On scroll to the top (`inject.js:8985-8995`), `loadMessage` (`inject.js:9116-9149`) reads 20 more records through `target_ts_idx`, range `IDBKeyRange.bound([name, 0], [name, key], false, true)` in `prev` order, where the key is the timestamp of the oldest shown message (`data-session`, `inject.js:8958` and `9132`). When nothing is left, it shows "This is the beginning of your conversation with …" (`inject.js:9138-9143`).
- Nightango reading: on each `OK`, `pmHistory` walks the whole database and keeps the last 100 entries of each member. Each entry carries its key `archiveTs`, the `ts` of the record as read (in seconds), never recomputed from the shown timestamp. For each member, `pmHistory` also tells whether the limit dropped older entries. A PM received in real time (`msg`, `msgoff`) also carries an `archiveTs`, `parseFloat(data[3])`, the key under which `saveMessage` archives it unless there is a collision. A sent PM has none before the next `OK`, which gives it the key of its entry.
- Paged reading: a truncated conversation shows a sentinel at the top. When nearing the top, `pmOlder` reads, through the same index, range and order as `loadMessage`, the 50 entries that precede the smallest loaded `archiveTs`, plus one that tells whether any are left. One read at a time. When nothing is left, the message log shows "This is the start of the messages saved in this browser.", like a conversation that the limit did not truncate. An older page goes through the same merge as on `OK` (see PMs received offline) and changes no unread counter. A conversation keeps the paging state of its first `OK`: on a reconnection, the last 100 entries say nothing about the pages already loaded.
- Nightango search: from 2 characters, the Chats search also looks in the text of PMs, after 300 ms without typing. `searchPm` reads `messages` read-only, one transaction per search, through a cursor on the primary key in `prev` order (most recent first). The text of each record comes from `parseContent`, never from the raw body, and is compared case-insensitively. Reading stops at 50 results plus one, which tells whether the limit cut the list. A result that arrives after a more recent input is ignored. On click, the conversation opens and the older pages load up to the message: same `archiveTs`, or, for a message shown without an archive key, the merge rule (see PMs received offline). An edit is found in its original. No frame and no HTTP call.
- The BetterChatango `searchMessage` (`inject.js:9089-9114`) is not used. BetterChatango calls it nowhere: it only searches one member, case-sensitive, in the body with tags stripped by a regex, stops at 20 results and only does `console.log`. Its "Search inbox" field (`client.html:239`) has no handler.
- `unread` is 1 or 0 (`saveMessage`, `inject.js:9039-9046`). BetterChatango archives a received PM as read only if `client.focus` is `private_message` and `client.private.focus` is its author (`inject.js:4063-4065`). The bridge never gives BetterChatango this focus: every received PM is archived unread, `msg` (`inject.js:4094`) as well as `msgoff` (`inject.js:4117`). A sent PM is archived read (`inject.js:4645`).
- Read marking, BetterChatango `Private.markRead({username, key})` (`inject.js:9245-9269`): cursor on `target_ts_idx` from `[username, 1]` to `[username, key]`, which sets `unread = 0`. BetterChatango calls it when a PM opens, with a string key (`inject.js:8959-8962`). In IndexedDB order, a string sorts after any number: all of the member's messages become read.
- The bridge makes the same write, through the same index and the same range (upper bound `''`), each time a conversation is read: opening, PM received while the conversation is open and visible, closing (`markPmRead`, called by `readPm` of `app/pm.js`). `tapPrivate` emits `pm` before BetterChatango archives the message: the bridge transaction is created after the current stack, so after the `saveMessage` one.
- Unread migration: without the private focus, BetterChatango archived as unread all PMs received before Nightango. Once per account, the bridge marks as read all records present when the database opens, before the private connection, then sets `pmReadMigrated` under `torch-skin:<username>` once the transaction completes. The msgoff of this connection, archived afterwards, stay unread. A timestamp filter would not work: a msgoff carries the sending time, earlier than the connection. The bridge also keeps the flag in memory from the start of the migration, so that it runs at most once per page: local storage can refuse the write (full on the shared st.chatango.com origin), and a migration redone on each opening of the database, so on each PM received, would mark every new PM read. A refused write is recorded in the diagnostic journal. Accepted limits: if the private connection was already open before Nightango, its msgoff become read. As long as local storage refuses the flag, each page load runs the migration again, and the unreads left by the previous page become read.
- Unreads: the database is their only source ([ADR-0012](adr/0012-pm-unread-from-history.md)). The counter of a conversation is the number of its `unread` entries, excluding edits (`pmUnread`: cursor on `target_ts_idx`, range of the correspondent). The state keeps only a copy, which `app/pm.js` reads again after each write: PM received, read, `OK`, import, message removal. Like read marking, this read is created after the current stack, so after BetterChatango archives the PM. On `OK`, the open and visible conversation is first marked read. A reconnection doubles no counter: nothing is added to the copy.
- Database unavailable (`indexedDB.open` failed, `pmArchived`): BetterChatango archives nothing. On `OK`, the app switches to an in-memory archive that keeps the unreads of the session, shows "Private messages aren't saved in this browser." at the top of Chats and records it in the diagnostic journal. Everything is lost on reload.
- No PM history deletion exists on the server side. `client.private.clearHistory(target)` erases the local copy through a cursor on `target_idx`. BetterChatango defines it without calling it. The "Delete" button of the official client does the equivalent.
- It reads `client.database.pm`, unset until the bridge opens the database before the first private connection, and then throws (`inject.js:9273-9287`). Delete conversation and Delete all (Settings, Privacy) remove a conversation only once `clearHistory` ran for it. Otherwise the conversation stays, since it would come back on reload, and a notification says so. Without a database (`pmArchived`), this browser keeps nothing that could come back: the conversation is removed.
- Message removal by BetterChatango: the `remove` entry appears on every non-ephemeral PM row, sent or received (`inject.js:8142-8144`). `messageAction` reads the `data-session` of the row, calls `removeMessage` and removes the row (`inject.js:7511-7519`). `removeMessage` deletes by primary key, without checking the member or returning a usable result (`inject.js:9073-9087`). `data-session` only exists on the rows read from the database (`inject.js:8958`, `9132`) and on one's own sent PMs (`inject.js:4646`). For a PM received in real time (`inject.js:4066`), BetterChatango removes the row but not the record, which comes back on reload.
- Message removal by Nightango: "Remove from this browser…" in the menu of a sent or received PM that has an `archiveTs`, after confirmation. The `ts` key is shared by all conversations, and `saveMessage` archives one second later a PM whose key is already taken (`inject.js:9064-9069`): the key read from the frame can then point to the PM of another member. `removePm` therefore reads again the record with key `archiveTs` in a `readwrite` transaction on `messages`, and deletes it only if its `target` is the conversation, if the author of `data` is the author of the message and if its content is the message's own. The content is compared by the PM key when the message carries one, because an applied edit changed its text, otherwise by the text read again through `parseContent`. For a keyed message, the same transaction also deletes, through `target_ts_idx`, the records of its author in the conversation that carry this key or target it (`<e…/>`): its edits, and its original when only an edit is shown. If left, they would come back on reload. The promise resolves to `true` at the end of the transaction that deleted, `false` otherwise or without a database. The message leaves the message log only after that. Only write: `delete` on the BetterChatango object store, without changing the schema.
- Style merge: the most recent style wins. Each member keeps the timestamp of the message its style comes from (`styleTs`), and a source merges its own only if its message is more recent (`mergeStyle` in `app/root.js`). The rule applies to real time (group and PM), the group history (`i` frames, received from newest to oldest), and the private history replayed on each `OK`. The own style always merges on sending (`setOwnStyle`) and takes as timestamp the greater of `styleTs` and the local time, so that it is not rejected when the local clock lags behind the server clock. Accepted limit: the timestamp archived by BetterChatango is off by a few seconds to a few minutes, so two very close PMs can be misordered.
- Export and import: BetterChatango offers the "Import messages" and "Export messages" buttons only on its own PM screen (`setImport`, `inject.js:9003-9033`). Nightango offers them in Settings > Privacy, and the prototype on its sample messages, in the same format. No frame or request: a file read by `FileReader` and a downloaded file (`Blob` and `download` link).
- File (BetterChatango `exportMessages`, `inject.js:9151-9163`): `JSON.stringify` of the raw array returned by `getAll()` on the `messages` object store, so the records `{ target, ts, data, unread }` in key order, type `text/json`, named `{client.user.name}_history.json`. A received PM has `target` as its author (2nd field of `data`) (`saveMessage`, `inject.js:9039-9046`), a sent PM has the account: `msg:{me}:{me}:unknown:{ts}:{flags}:{body}` (`inject.js:4645`). The Nightango export (`exportPm` of the bridge) writes the same file, byte for byte, `unread` included.
- BetterChatango import (`importMessages`, `inject.js:9165-9189`): `JSON.parse` of the file, then a `readwrite` transaction that does `put({ target, ts: parseFloat(ts), data, unread })` for each entry, without any validation. `put` overwrites the record with the same `ts`, whatever its member, and `unread` is copied as is.
- Nightango import (`importPm` of the bridge, filtered by `screenPmRecords`), intended differences from BetterChatango:
  - An unreadable file or one that is not an array writes nothing ("This file is not a BetterChatango message history.").
  - A record is written only if `target` is 1 to 20 characters `[A-Za-z0-9_-]`, if `ts` is a finite positive number, if `data` starts with `msg:` and has at least 7 fields separated by `:`, and if its author is `target` or the signed-in account, case-insensitive. The others are skipped. Only these four fields are written, `target` in lowercase like every name in Nightango: older pages, read marking, the unread count and message removal look a correspondent up by its lowercase name.
  - File from another account: when all skipped records were skipped for a foreign author, nothing is written ("This file holds another account's messages. Nothing was imported."). Its received PMs would pass the filter one by one, their author being `target`, but its sent PMs carry another account. A file exported by this account has no foreign author: BetterChatango archives a received PM under its author and a sent PM under the account, in a database specific to the account.
  - `add` instead of `put`: a `ts` key already present is not overwritten and counts as already saved.
  - Every imported record is written as read (`unread: 0`), whatever its `unread` in the file: a restore lights up no conversation.
  - The report follows the end of the transaction: "Imported N messages. M already saved, K skipped." An aborted transaction writes nothing and says so.
  - The conversations are then read again as on `OK` (`loadPmHistory`), without duplicates. The import may have added entries older than the last 100: a conversation from which the limit then drops entries resumes paged reading, even if it had finished it. The imported content is shown only through `parseContent`, like the whole history ([ADR-0004](adr/0004-member-html-never-injected.md)).

### PMs received offline

- `msgoff` frames are delivered only once, right after `OK` on the private connection.
- Like BetterChatango, the bridge therefore opens the history database before the private connection, so that these messages are archived in it.
- The merge with the history creates no duplicate. BetterChatango archives a timestamp different from the shown one: an already shown message covers a single history entry, compared with a snapshot of the shown messages (`mergePmHistory` in `app/pm.js`, on `OK`, after an import and for each older page). An entry whose `archiveTs` is that of a shown message is that message, and a message that already carries an `archiveTs` covers no other. For the others, when both carry a key (see PM key and edits), the same key makes the same message, even if its text changed. Otherwise, it takes the same author and the same content, within two minutes. The shown message that covers an entry takes its `archiveTs`.
- A single grouped notification announces them: "N messages received while you were away."

### PM key and edits

- BetterChatango identifies each PM it sends by `<i{base36}/>` at the start of the body (`inject.js:5177`). The PM key is this identifier followed by `=` (`<i([a-z0-9]{7,8})\/>`, `inject.js:7842-7848`, `8950`, `9131`). `parseContent` returns it in `key`, decoded like `editId` so that the two compare directly. The bridge passes it on for `msg`, `msgoff` and the private history.
- An edit is a new PM, with its own `<i…/>`, that carries `<e{ref}/>` before the content, in the same `msg:` body (`inject.js:5231-5241`). The ref is the key of the original, in the message reference format (see Sending).
- On receipt, BetterChatango applies it to the original with the same key and the same author, and hides the edit message (`displayEdit`, `inject.js:5497-5536`). Nightango does the same, in real time and in the history merge (`app/root.js`): the original keeps its place and its timestamp, takes the text and media of the edit and shows "(edited)". In real time, an applied edit counts neither as an unread nor as a notification.
- An edit whose original is not loaded is shown as a received PM, marked edited. It takes the key of the original, which the archive and the following edits target.
- Sending an edit (BetterChatango `sendMessage`, `inject.js:5236-5241`, Edit entry on one's own PM rows, `inject.js:8140-8142`): `msg:{name}:<n…/><i{id}/><m v="1"><g …><e{ref}/>{content}</g></m>`, the ref being the PM key of the original. The bridge inserts `<e…/>` right after `<g …>`, where BetterChatango puts it, never together with `<r…/>`. Failure text: "Your message could not be edited." Nightango offers "Edit message" on one's own PMs that carry a key, sends nothing if the text did not change, and refuses the tenth edit like groups (`inject.js:5466-5467`). Chatango does not send a PM back to its author: the sent edit applies to the local original through the same path as a received one.
  - Edit count: each applied edit is counted once by its own PM key (`editKeys`), since each `OK` replays from the history the edits already applied live.
- Reply (BetterChatango `sendMessage`, `inject.js:5253-5258`, Reply entry on every PM row, `inject.js:8128-8139`): `msg:{name}:<n…/><i{id}/><m v="1"><g …><r{ref}/>{content}</g></m>`. The ref is the PM key of the original, in the message reference format (see Sending). The bridge inserts `<r…/>` right after `<g …>`, where BetterChatango puts it. Failure text: "Your reply could not be sent."
  - Receiving (BetterChatango `displayReply`, `inject.js:5406-5455`, called for group rows and PM rows, `inject.js:8213-8222`): the original is shown above the reply only if it is loaded. The bridge passes `replyId` for `msg`, `msgoff` and the private history. Nightango looks for the message with this key in the conversation, otherwise shows "Original message not loaded".
  - A PM without a key, sent by the official Chatango client, has no Reply in Nightango: the reply could not point to it.
  - How the official client renders `<r…/>` and `<e…/>` in a PM is not checked. In Reply and Edit mode, the composer of a PM or a group says under the reply or edit line, with the `info` icon: "Only visible to Nightango and BetterChatango users." (owner's decision, 2026-10-30), since BetterChatango renders both (`inject.js:5407`, `5514`).
- Quote (BetterChatango `sendMessage`, `inject.js:5245-5252`, Quote entry on PM rows, `inject.js:8136-8138`): `` msg:{name}:<n…/><i{id}/><m v="1"><g …>{emphasis}@{name}: `{quoted}` {content}</g></m> ``, no reference. Same rules as the group quote (see Sending), except for the place: after `<g …>` and the openings of the style, read from the BetterChatango checkboxes, `<B>`, `<I>`, `<U>` (uppercase in a PM, `inject.js:5207`) then `▓` for the strikethrough (`inject.js:5185`). Failure text: "Your quote could not be sent." Nightango offers "Quote message" on every PM that has text, key or not.

### PM style

- The body has the form `<n{name color}/><m v="1"><g x{size}s{color}="{font}">…</g></m>`. The group format is different: `<f x{size}{color}="{font}">`. Sources: chadango `PrivateFontStyleRe`, BetterChatango `renderMessage`, official client.
- The font must be read on the `<g x` or `<f x` tag. BetterChatango has a greedy regex that mistakenly reads `h="93"` from an `<i>` tag.
- Font size of a member: BetterChatango applies it with 11 = 100%, clamped between 82 and 200% (`fontScale`). Nightango uses the same scale (`fontPercent`), and a tag without a size is 100%.
- Emphasis: the BetterChatango style and Markdown write `<b>`, `<i>`, `<u>` (`inject.js:5181-5191`, `mdParseStyle` `12260-12290`), in uppercase in PMs (`inject.js:5207`). BetterChatango marks the strikethrough of a PM with `▓…▒` (`inject.js:5185-5187`). On rendering, its emphasis allowlist keeps `<[biusp]>` and `</[biuspf]>`, turns `<strike>` into `<s>` in PMs and a `▓…▒` pair into `<s>`, in groups as in PMs (`renderMessage`, `inject.js:7819-7822`). `<i s="…"/>` (media) and `<i{id}/>` (PM identifier) do not open italics. `parseContent` does the same: a `▓…▒` pair becomes a struck segment and its markers leave `text` (previews, `pmContentKey`), a lone `▓` or `▒` stays as text.
- BetterChatango reads the sending style from its `msgstyles` form (bold, italic, underline, strikethrough, size, colors, font), only if the user style is on (`this.user.style`, `inject.js:5145-5155`). Nightango writes the own style there right before each send.
- Strikethrough: the `.fa-strikethrough` checkbox (`inject.js:5150`) only acts in PMs. BetterChatango then adds `▓` before the text, after `<b>`, `<i>`, `<u>`, and `▒` after it, before their closing tags (`inject.js:5185-5187`). In groups, it has no effect. The bridge ticks the checkbox according to the own style and lets `client.sendMessage` build the body. Strikethrough is not part of the account style: `msgstyles.json` only loads bold, italic and underline (`inject.js:1315-1335`). In BetterChatango too, it is a local setting.

### PM restriction

- BetterChatango checks whether the PMs of the signed-in account are restricted. The first time its PM screen opens, if `client.settings.privacy.private_messages.check_pmr` is on, it calls ``fetch(`//api.vissle.me/v1/pmr/${client.user.name}`)`` (`inject.js:10601-10644`, call `inject.js:10631-10643`).
- Setting: `check_pmr`, true by default (`inject.js:9689`). Switch "Check my PMR status when private messages are initiated" in the BetterChatango screen (`client.html:2618-2619`), saved in `localStorage["settings"]` like the other settings (see BetterChatango startup settings).
- Call: GET, without key or password. `fetch` sends no cookie to another origin. The name is that of the signed-in account, never another ([ADR-0005](adr/0005-visitors-own-profile-only.md)).
- Response: BetterChatango reads it only on a 200 status, as JSON, and only looks at the `pmr` field. False or missing: "Your private messaging status is in good standing." True: "You appear to be private message restricted." Any other status: nothing. BetterChatango keeps the message in `client.private.pmr` and replays it each time its PM screen is shown again (`inject.js:8859-8861`).
- Limit: only the `pmr` field is known. The code does not say what the restriction covers, nor how vissle establishes it. Scope, according to the project owner (2026-10-24) and not according to the code: a restricted account can send PMs only to accounts that added it as a friend. BetterChatango also sends `msg:{torch.server}:getpmr` itself when it receives `seller_name` on the private connection (`inject.js:4045-4048`), including in live. Its link with this call is not established.
- In live, the BetterChatango call never goes out: the bridge opens the private connection itself, without going through the BetterChatango screen, whose PM tab it disables at sign-in (see Calls BetterChatango makes itself). The bridge therefore makes the same call (`pmrStatus`, no argument), with the name read from `client.user.name`, never from the page. Setting off or unreadable, on request as when the private connection opens: no call. Otherwise, one call at most per page load, after the private connection opens. The interface requests it on each `pmReady`, as BetterChatango does when its PM screen opens, and when Privacy opens: the bridge keeps the first response, later requests do not call vissle. It returns `restricted` (`pmr` true), `ok` (`pmr` false or missing) or `unknown` (status other than 200, unreadable JSON, network error).
- Privacy, Private messages section, presents `check_pmr` in live: the switch "Check my private message status" writes it in place then rewrites `localStorage["settings"]` (`setSetting`), and is missing if the BetterChatango settings are unreadable. With the setting on, the section shows what the response establishes, and only that: "vissle reports no restriction on your private messages.", "vissle reports that your private messages appear to be restricted." or "vissle could not check your private message status." Setting off, or response not yet received: no status line. The prototype has neither the switch nor the line.
- `restricted` response, setting on: the Private messages column shows under its header the banner "Your private messages are restricted", "People might not receive your messages." Once closed, it comes back only on the next page load. Setting turned off in Privacy: the banner disappears. `ok`, `unknown` or prototype: no banner.

### Friend presence

On the private connection. Timestamps are in seconds. `None` or 0 means unknown.

- `wl`: quadruplets `name:timestamp:state:minutes`, state `on`, `off` or `app`. In `on`, non-zero minutes mean idle. In `off`, the timestamp is the last online time.
- `wladd:name:state:value`: idle minutes in `on`, timestamp in `off` or `app`. `wladd:name:invalid` for an unknown name.
- `wlonline:name`, `wlapp:name` (signed in from the mobile app), `wloffline:name:timestamp` (ch.py source).
- `status:name:timestamp:state`, state `online`, `app` or `offline` (ch.py and chatango-lib sources). This frame does not say whether the account is idle: an idle state already known is kept. BetterChatango only uses it for its PM screen.
- `presence` (response to `getpresence:a;b`): triplets of name, minutes, state (`online`, `app` or `offline`). In `online` or `app`, the minutes are idle time. In `offline`, they give an approximate last online time.
- `connect:name:value:state` (response to `connect:{n}`, BetterChatango `connect` handler, `inject.js:4120` to `inject.js:4166`): presence of a correspondent, friend or not. State `online`: online if the value is 0, otherwise idle for `value` minutes (`inject.js:4159`). `app`: signed in from the mobile app. `offline`: the value is the last online time in seconds (`inject.js:4160`). Refusals: `invalid`, the name "does not exist or is a group chat" (`inject.js:4124` to `inject.js:4131`), `nouser`, the name "is not associated with a Chatango account" (`inject.js:4132` to `inject.js:4134`), and an empty name, "Username does not exist or is a group chat." (`inject.js:4164`), which the bridge ties to the last name sent. Like BetterChatango, the bridge ignores any other state. The response only carries presence: BetterChatango reads the history from its local database (`inject.js:8939` to `inject.js:8968`).
- BetterChatango sends `connect:{n}`, name in lowercase, each time a PM opens: click on a conversation (`inject.js:10212`), `/chat name` (`inject.js:7354`), "Message" from a profile (`inject.js:7580`), Chat form (`inject.js:10590`) and avatar (`inject.js:756`). Never on close: it sends `disconnect:{n}` only after a block (`inject.js:7585`). The bridge sends `connect:{n}` when the shown conversation switches to a correspondent other than the one of the last request, if the private connection is open. New private message sends it before opening the conversation and waits for the response.
- Each `OK` starts a new private session: Chatango no longer pushes `status` for the correspondents connected before, and BetterChatango builds a new `client.private` (`inject.js:4031` to `inject.js:4037`), whose `focus` is false. The bridge forgets the last request on `OK`, then sets the shown conversation again on the new `client.private` and sends `connect:{n}` for it.
- Chatango pushes presence only for friends and for the correspondents connected in the current private session. For the others, the group participants and Meet people leave a presence that nothing updates. The app therefore sends `getpresence:a;b` (BetterChatango source, Meet people, `inject.js:9387`) for the correspondents of the Chats list who are not friends, except the shown conversation, the 40 most recent at most (the size of a Meet people page): once the history and the friend list are loaded, then after each `OK` (before the friend list, a friend would get the approximate last online time instead of the exact one of `wl`), then when the page is visible again or every minute while it is visible, if the last request is older than 5 minutes (`PRESENCE_REFRESH`, `app/root.js`). chadango sends the same request as `statuslist:a;b`, for the same `presence` response.
- The bridge does not call the BetterChatango `connect` handler, as for `DENIED`. This handler goes through `Private.setFocus` (`inject.js:8875` to `inject.js:8995`), which opens the BetterChatango PM screen, sets `client.focus` to `private_message`, adds the person to its list and marks its database read, while Nightango manages these states itself. With `check_block` (false by default, `inject.js:9691`), it also calls `api.vissle.me/v1/profile/{name}?get=status` (`inject.js:4142` to `inject.js:4157`), excluded from the closed list of allowed HTTP calls ([out-of-scope note](../.out-of-scope/blocked-by-member.md)).
- The bridge derives `lastOn` from it (milliseconds, 0 if unknown). Going offline without a timestamp takes the current time (`app/root.js`). The Chats and Friends rows show this date at the top right for an offline friend ("3 h ago").

## Media

- Tag `<i s="…" [w h]/>`, in groups as in PMs.
- Only known prefixes (official client): `vid://yt:{11-character id}`, `img://cam:{id}` and `img://lib:{id}`. The last two give `https://chatango.com/pmmessageimg?i={id}` (BetterChatango). The rest are https URLs.
- BetterChatango loads the YouTube oEmbed automatically, for every YouTube link received, in every group (`client.renderYouTube`, `inject.js:7144-7171`). In live, the bridge neutralizes it at sign-in (see Calls BetterChatango makes itself). Nightango never calls it, and the `youtube-nocookie.com` iframe is created only on click.
- YouTube links as text: BetterChatango turns a YouTube link into a `vid://yt:` tag only in PMs (`inject.js:5208-5211`). In groups, the link arrives as text and BetterChatango embeds it on rendering with the regex `(?:https?://(?:(?:\w+\.)?youtube\.\w{1,3}|youtu\.be)(?:.*v=|/\w+/|/)([\w-]{11})[^<\s]*)` (`inject.js:8256-8259`). `parseContent` applies the same regex to each link in the text and adds `{ kind: 'youtube', id }`, unless the message already carries this media, through a `vid://yt:` tag or another link. The link stays in the text. The `t=` and `list=` parameters are ignored. The rendering is that of the tag: thumbnail, and iframe on click.
- Video and audio files: BetterChatango embeds `https?://….(mp4|wmv|webm)` as `<video controls>` without waiting for a click (`inject.js:8089`, `crawl` `1102-1134`), and the first `….(mp3|ogg|wav)` URL of a message as `<audio>` after a click, except for a host in its allowlist (`embedAudio`, `inject.js:6423-6642`). `parseContent` picks out in the text the https URLs that end with `.mp4` or `.webm` (`{ kind: 'video', url }`) and with `.mp3`, `.ogg` or `.wav` (`{ kind: 'audio', url }`), query and fragment allowed, case ignored. `http` URLs, `.wmv` and other extensions stay links. The link stays in the text.
- With `embedVideos`, a video or audio file, whatever its host, is shown as a "Play video" or "Play audio" button followed by the host. The `<video controls>` or `<audio controls>` is created only on click, then starts. For a trusted host, it is created without a button and without autoplay. Without `embedVideos`, or if the file does not load, it stays a link that goes through the link warning. `<video>` and `<audio>` do not accept a `referrerPolicy` attribute: the host receives the referrer according to the page policy, as for the YouTube iframe. The button names the host before the click, which counts as consent.
- TikTok links as text: BetterChatango does not embed them. `parseContent` adds `{ kind: 'tiktok', id, url }` for a post link `https?://(www.|m.)tiktok.com/@{user}/video/{id}` or `/photo/{id}`, and `{ kind: 'tiktok', url }` for a short link `tiktok.com/t/{code}/`, `vm.tiktok.com/{code}/` or `vt.tiktok.com/{code}/`, which does not carry the post id. A profile, tag or other TikTok link stays a link.
- With `embedVideos`, a TikTok link is shown as a "Play video" button followed by the host, trusted host or not. On click, the TikTok embed player iframe is created and starts. For a short link, the click first asks the loader for the post id (see Allowed HTTP calls), and the button reads "Loading video" meanwhile. If TikTok gives no post id, a toast says why and the embed turns back into a link that goes through the link warning. Without `embedVideos`, it stays a link. The prototype has no loader: a short link there turns back into a link on click. TikTok's oEmbed is not used: its reply asks for TikTok's `embed.js` script in the page ([ADR-0014](adr/0014-tiktok-embed.md)).
- Nightango reuses neither the oEmbed nor the BetterChatango `wsrv.nl` proxy (`inject.js:1116`).

## File uploads (vissle)

- BetterChatango Upload window: the `fa-fire` icon targets `${torch.domain}/chatango/upload`, that is `https://vissle.me/chatango/upload`, and limits the picker to `.png, .apng, .jpg, .jpeg, .gif, .bmp, .webp, .mp3, .ogg, .wav, .mp4, .wmv, .webm` (`inject.js:2911`, `inject.js:7548-7553`). The form has a single file field, `filedata` (`client.html:3345-3347`, `client.post` allowlist, `inject.js:4698-4702`). BetterChatango sends it through `client.post(server, form, { progress: true, status: {…}, key: true })` (`inject.js:11048-11067`).
- `{ key: true }`: BetterChatango adds the vissle session key `key` to the form, never the password (`inject.js:4744-4745`). Our code never reads this key.
- Nightango: `liveBridge.uploadFile(file)` calls `client.post('https://vissle.me/chatango/upload', form, { key: true })`, with the single field `filedata`. Never `progress`, never `credential` (see Allowed HTTP calls). Without `progress`, `client.post` sends the form through `fetch`, as `FormData` since the URL does not end with `chatango/updateprofile`, and resolves with the response text without posting anything (`inject.js:4830-4855`). Reading the response follows the same CORS rules as the BetterChatango `XMLHttpRequest`.
- Responses, read by BetterChatango in its `progress` branch (`inject.js:4774-4809`):
  - `data:{path}`: the file is hosted by vissle, at `https://vissle.me/{path}`. The bridge accepts only a `{path}` made of `[A-Za-z0-9._/-]`.
  - `unauthed`: vissle refuses the session (BetterChatango shows "Relogin required."). Nightango: "vissle did not accept your session. Reload the page and sign in again."
  - Any other response (`error:{text}` included) or network error: "The file could not be uploaded. Try again." The text returned by vissle is never shown.
- Why not `progress`: this branch (`inject.js:4758-4829`) posts `https://vissle.me/{path}` itself through `client.sendMessage(...)` without a group (`inject.js:4786`), so in `client.focus`, or to `client.private.focus` in PMs (`inject.js:5139-5140`): the group or PM that BetterChatango believes is open, not necessarily the Nightango one. It also touches the hidden BetterChatango screen (`.chat-upload`, `.external-modal-avatar`, `inject.js:4780`, `4798`, `4813`) and loads `noimage.jpg` from vissle if the file field is empty (`inject.js:4760-4765`). The only cost of leaving it out: no progress percentage.
- Limits of the `fetch` path: the HTTP status is not checked (the BetterChatango `status` handlers only serve the `progress` branch, `inject.js:4826`), and `client.post` refuses a request while another one is in progress, rejecting with the URL of that one (`inject.js:4752-4755`). Nightango reports it: "BetterChatango is busy with another request. Try again in a moment."
- Picking: the picked file waits in the composer of its group or PM, with a local preview (object URL, nothing leaves the browser) and the note "vissle.me hosts it when you send. Anyone with the link can open it." Nothing is uploaded before Send. A file picked in one PM is never offered in another.
- Posting: on Send, Nightango uploads the file, then posts a single message, the typed text followed by the link, itself through `actions.sendGroup` or `actions.sendDm`, with the reply, the quote and the channel of the composer, in the group or the PM where Send was pressed, fixed at that moment. Send stays disabled in that composer until the upload ends. "File sent." is shown only after the `data:` response and the sending of the frame. If the upload fails, the text goes back to the field and the file stays picked. If the frame does not go out, the text and the link go back to the field and the link can still be copied from the notification.
- Display: a link that the message shows as a media (image, video or audio file, YouTube) leaves the shown text, `mediaLinks` and `shownParts`. The raw text keeps it: Copy text copies it.
- The prototype sends nothing: "Uploading media is not part of this prototype."
- Same upload for the Premium background image (Profile page), after confirmation: the returned link fills the image field and is posted nowhere.

## Profile activity (vissle)

- Transport: `POST https://vissle.me/track1/activity`, body `JSON.stringify({action:'activity', profile, page, order, get})` as `text/plain`. No authentication (source `vissle.me/js/track.js`).
- vissle sends no CORS header: the page cannot read the response with `fetch`. Hence the `GM_xmlhttpRequest` bridge in the userscript sandbox ([ADR-0003](adr/0003-two-context-loader.md)).
- Tracker: the tag `<script src="//vissle.me/profile/{n}"></script>` in the mini profile bio. BetterChatango detects it with `/<script src="(?:https:)?\/\/vissle.me\/profile\/(\d+)"><\/script>/` (`inject.js:1472`, `4889-4890`).
- Nightango adds and removes it in the Visitors section of the Profile page, like BetterChatango. Adding (`inject.js:1478-1487`, `1521-1541`): `\n<script src="//vissle.me/profile/512"></script>` at the end of the bio, if the bio is shorter than `2000 - ("\n" + tag).length` characters. Removing (`inject.js:1488-1493`): replacing `/(\n)?(<script src="(?:https:)?\/\/vissle.me\/profile\/\d+"><\/script>)/` with an empty string. A tracker already present keeps its `n`. Only the bio draft changes: the bio then goes out through `updateprofile` (Own profile).
- The shown status comes from the saved bio. Nightango never loads `vissle.me/profile/{n}`: the tag is bio text, which `RichText` does not render ([ADR-0004](adr/0004-member-html-never-injected.md)). The BetterChatango tracker options (`n` = 512 + flags, `client.html:2106-2220`) and its "track" panel stay in BetterChatango.
- Response: `{get:[{user, name?, action, time, msg?}]}`, or `{error}` in a 200 response.
- Paging: 16 items per response, of which 15 are shown. Next page: `page` = `time` of the last shown item.
- `get`: `all|log|like|dislike|msg|refer`. `order`: `desc|asc`.
- No real time: the vissle socket.io refuses the st.chatango.com origin.

## Linked accounts (vissle)

- Transport: `GET https://vissle.me/api/v1/who/{name}` through `fetch` from the page, without options, like BetterChatango (`inject.js:7452-7477`): no cookie, since the origin differs, and no credential. `{name}` is an account validated by `ACCOUNT_NAME`, never a guest. One call per click on "Who is this", without cache ([ADR-0010](adr/0010-linked-accounts-on-request.md)).
- Response: JSON `{target, definite, linked, strong, medium, weak}`, each level a list of names. BetterChatango requires `target`, then shows the total and each non-empty level, in this order.
- `parseWho` requires `target` and reads only the strings of the five lists. Any other field is ignored. `target` is not shown: the dialog names the clicked account. The names are rendered as text.
- "Who is {name}" dialog: the total, each non-empty level with its count and one card per name, and a line that says this is the vissle estimate. Without names: "vissle has no linked accounts for {name}." Unreadable JSON or without `target`: "vissle sent an answer Nightango can't read." `fetch` rejected: "vissle could not be reached. Try again later." The result lives in the dialog: closing it forgets it, and nothing is stored or logged.
- Account card: lowercase name validated by `ACCOUNT_NAME`, `thumb_m.jpg` avatar and mini profile (`mod1.xml`, `custom_profile.css` if Premium) read as in Meet people, four requests at a time, through the public GETs of the closed list. A name that is not an account stays as text, without avatar or request. Click on a card: the member card of the account opens over the list, and closing it returns there without calling vissle again. A member card action that leads elsewhere (PM, group in common, ban) also closes the list and the original member card.

## Frames used and their source

Chatango returns no request identifier. For three requests, the bridge waits for the response itself, recognized by its key, and emits a fact if it does not arrive in time: `wladd:{n}` (8 s, op `friendTimeout`), `searchban:{q}` in a group (8 s, op `banSearchTimeout`, a more recent search replaces the wait of the previous one) and `connect:{n}` sent by New message (5 s, op `pmChecked` with `timeout`, and `asked` on the response that was awaited). A response that arrives after the delay is still emitted.
